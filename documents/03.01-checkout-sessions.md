# POST /api/v1/checkout-sessions

Creates a payment or subscription checkout session. Requires auth ([HMAC or Firebase ID Token](02-authentication.md)).

## Request body

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `external_ref` | string | Only for HMAC — ignored (and not required) for Firebase ID Token, where it's always derived from the token instead | Your identifier for the end user |
| `plan_ref` | string | Yes | Free-form label you assign, e.g. `premium_1m` — PayGate doesn't need to know your plans in advance |
| `amount` | integer | Yes | Smallest currency unit (e.g. cents for USD, whole units for currencies like VND — check with your gateway operator which convention their Stripe account uses), must be `> 0` |
| `currency` | string | Yes | Exactly 3 characters (e.g. `USD`, `VND`) |
| `mode` | string | Yes | `"payment"` (one-time) or `"subscription"` |
| `interval` | string | Only if `mode=subscription` | e.g. `day`/`week`/`month`/`year` (not validated against a fixed list at this endpoint — use a value Stripe accepts) |
| `interval_count` | integer | Only if `mode=subscription` | Must be `>= 1` |
| `success_url` | string | Yes | Where the end user lands after a successful payment |
| `cancel_url` | string | Yes | Where the end user lands after cancelling |
| `payment_method` | string | No | `"stripe"` or `"test"` — see below |
| `test_card_code` | string | Only if `payment_method="test"` | See [Testing](03.04-testing.md) |

## The `payment_method` field — you usually don't need it

Omit `payment_method` entirely in production integrations. What happens next depends on your app's configured environment:

- **`production`** environment: PayGate defaults to `stripe` and returns a real Stripe `checkout_url` immediately.
- **`staging`/`test`** environment: PayGate returns a `checkout_url` pointing to its own hosted picker page instead ([GET /checkout/{public_token}](03.03-checkout-page.md)) — the end user chooses Stripe or a test payment there. This lets your QA process exercise both paths without you writing any extra integration code.

Only send `payment_method` explicitly if you're calling this endpoint from automated tests/QA scripts and want to skip the picker page.

If you send a `payment_method` your app's environment doesn't allow (e.g. `"test"` against a `production` app), you get `403 payment_method_not_allowed`.

## Response — success (Stripe or the picker page)

```json
{ "success": true, "data": { "checkout_url": "https://checkout.stripe.com/c/pay/cs_test_..." } }
```

or, when the picker page applies:

```json
{ "success": true, "data": { "checkout_url": "https://payments.example.com/checkout/9f3a...64hexchars" } }
```

Either way: redirect the end user to `checkout_url`. Don't try to distinguish the two cases — both eventually redirect back to your `success_url`/`cancel_url`.

## Response — `payment_method="test"` (synchronous, no redirect)

Resolves immediately based on `test_card_code` (see [Testing](03.04-testing.md)) — no Stripe call, no `checkout_url`:

```json
{
  "success": true,
  "data": {
    "status": "completed",
    "subscription": {
      "plan_ref": "premium_1m",
      "status": "active",
      "current_period_end": null
    }
  }
}
```

`current_period_end` is `null` for `mode="payment"` or a lifetime plan; otherwise an ISO-ish `"YYYY-MM-DD HH:MM:SS"` string. A declined test card returns an error instead (`invalid_card_details` / `insufficient_funds`) — see [Errors](05-errors.md).
